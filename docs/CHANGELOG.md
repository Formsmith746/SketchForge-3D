# Changelog

## Unreleased

- Pointed everything that names a repository at this one. Forking left several references on the project this was forked from, and because nothing asserted them, nothing complained. Three of them were not cosmetic: the desktop updater's release feed asked *upstream* what the newest version was, and upstream's newest is older than ours, so every desktop build we ship had an updater that could never offer an update; the self-hosted "update" button compared against upstream's `package.json` and would have pulled upstream's code over this one, replacing every feature here; and the source-code link offered upstream's source, where the AGPL expects a network user to be offered the corresponding source of the build actually running. The container image paths in the README, the REST API guide and the ghcr compose file pointed at upstream's image too, so a reader following our own instructions ran a build with none of this work in it.

  A test now asserts each of them, including that the attribution still points at the original author -- repointing what is functional should not quietly erase credit. The sponsor link and the upstream issue references stay as they are, because they are correct.

- Fixed `POST /booleans` and `POST /groups` answering `201` with a group that is really just the unchanged solid, when none of the holes met it. The kernel's `cutAll` hands the solid back untouched in that case and says nothing about having done so, and this path never compared the volume before and after -- so a hole placed at the wrong coordinates was stored and reported as a successful cut. A script has no picture to check that against, which makes it worse here than the same mistake would be in the editor, where the result is visible. The editor's own boolean has compared those two volumes since it moved to the exact kernel -- its comment reads "the mesh paths treat that as a failed cut rather than a group, and so does this" -- and the server now uses the same comparison and the same threshold, so the two agree about what counts as a cut. The measurement is reported by the geometry layer and refused by the two routes, before anything is written, which keeps a hole that deliberately misses usable for observing where a placed solid lands -- the technique the rotation regression test uses.

- The server also now asks whether a cut's result is geometry the kernel considers valid, before storing it. It is stored in `cadBrep`, which a later fillet or a STEP export reads, so an invalid result was a failure deferred to whoever opened the project next. The check deliberately accepts a compound rather than demanding a single solid, because a cut can legitimately split one body into several -- which is what `POST /parts` exists to separate -- and a test pins that, since requiring a single solid is the obvious "tidy-up" that would refuse real results.

- Fixed `POST /shapes` dropping parameters it documents as applicable. A request for a tapered box -- `{"kind": "box", "taperTopWidth": 2}` -- came back as a straight box with a `201`, because the shape was built by a branch per kind that named only the parameters that kind cannot be built without, and no branch mentioned taper. `PATCH` applied the same fields all along by looping over the shared parameter table, so creating a tapered box and patching one produced different shapes, and the only way to discover it was to create one and then patch it. Create now reads the same table, so a parameter added to it works on both paths without anyone remembering to touch a branch. A kind's own default still wins where it has one -- an unreadable `sides` on a pyramid is 4, not the table's generic 96 -- and a parameter the kind does not claim is still not applied, which is the direction `PATCH` refuses with a 422.

- A sphere, a dome, a torus and a tapered cone can now be hollowed. `POST /api/v1/shell` refused all of them, and the reason given -- that OCCT will not offset a continuous curved surface -- was wrong. OCCT offsets an analytic sphere, cylinder, cone and torus perfectly well; what it refuses is a **spline** skin. The sphere was refused because this app built one as a revolved spline even when all three radii matched, so the most obvious hollow part anybody would ask for -- a ball -- was turned away by a limit it did not have. A ball of equal radii is now built as a true sphere and hollows to the volume the arithmetic says: 40mm across with a 2mm wall is 4/3 pi (20^3 - 18^3) = 9081.2972mm^3, exactly, centred exactly on its own centre.

- That also makes a sphere's volume right everywhere else it is used. OCCT's ellipsoid is a revolved spline whose volume is a fraction of a percent out -- 4187.0 against 4188.79 for a 20mm ball -- and a boolean cut was cutting with that approximation. An elliptical ball is still a spline, still approximate, and still cannot be hollowed; only the equal-radii case can be analytic.

- The documented list of what hollows is now the measured one, with the real reason beside it. A pointed cone cannot be hollowed because offsetting inwards from an apex has nowhere to go -- give it a `topRadius` and it works. A `tube`, `ring` or `roundRoof` cannot, because their walls are built by extruding a profile, which is a spline surface however round it looks. A `loft` cannot, for the same reason. Each of those answers `422` saying which.

- The dark highlight that shows where a hole will land now agrees with the cut it is previewing, and there is one place that decides what agreeing means. This app had three allowances on a hole -- 0.05mm on the mesh cut, 0.01mm on the preview, and nothing at all on the exact cut that now commits -- spread over two files with no stated relationship between them, so nobody could say what the highlight was promising. They are all in `cutterPadding` now, in a table, with the one rule each obeys: the preview shows the hole as drawn, which is what the exact cut removes, grown only by a separation its own evaluator needs. It could instead have mirrored whichever backend was about to run, and shown the mesh path's 0.05mm where that one serves -- but nobody can see which backend ran, and that overcut is a defect of the fallback rather than anything anyone asked for.

- That separation is not negotiable, and the measurement is worth recording because the comment that used to justify it understated the problem. On a 40x40x10 plate with a 12mm blind pocket whose floor is flush with the plate's top face, the preview's `HOLLOW_INTERSECTION` returns 179 triangles in 11.6ms with the 0.01mm separation, and had not returned after four minutes with none. Coplanar faces fed to that evaluator do not merely multiply the triangle count, as was thought; they stop it coming back.

- Fixed the preview under-separating a tapered hole, which is how dragging one over a solid could hang the editor. The highlight grows the hole by scaling its drawn mesh, and a scale grows a narrow section by less than a wide one: a cutter tapering from 20mm to 2mm, scaled to clear a hundredth of a millimetre at its mouth, cleared a thousandth at its tip -- which is the condition above. The growth is now scaled by the taper's own ratio, so the narrowest section clears the full separation, and capped at the 0.05mm this app already treats as an acceptable allowance on a cut, so a cutter tapering to nothing cannot grow the highlight without bound.

- The preview is deliberately still a mesh operation rather than an exact one, and that was measured rather than assumed. An exact cut of a single round pocket takes 3.6ms of kernel time, 8.5ms for a tapered one and 65ms for a plate with three holes, and it would have to go through the CAD worker and wait on a 22MB kernel load the first time -- against a highlight redrawn on every pointer movement. A preview that is right and late is worse than one that is right to a hundredth of a millimetre and immediate. What #48 left behind was three uncentralised constants and an untested relationship, not a wrong number: before it, the preview showed 0.01mm where the mesh cut removed 0.05mm, so it was four times further from the truth than it is now.

- The editor's mesh primitives are no longer built twice. Seven of them -- the roof, the wedge, the pyramid, the barrel roof, the dome, the torus and the tube -- existed as one copy in `WorkplaneViewport.tsx` for the thing on screen and a second, near-verbatim copy in `SketchForgeEditor.tsx` under `createBoolean*` names for the operands of a mesh boolean. The vertex arrays, the index arrays and the attribute setup were byte-identical; what differed was the last statement, and in one case the shading. Both now come from `lib/primitiveGeometry.ts`, with the two real differences preserved as options rather than reconciled: `indexed` for the boolean path's index buffer, and `halfSphereNormals` for the dome's analytic-or-averaged normals. Nothing about what gets drawn or cut has changed, and that was checked rather than assumed -- both old copies were extracted and compared attribute by attribute against the new module across five sets of dimensions and every tessellation parameter they take, 175 comparisons, all identical.

  The reason this is worth a changelog entry is not the line count. A copied builder is invisible until the copies disagree, and these two had already begun to: the viewport computed analytic ellipsoid normals for the dome with a dedicated flat normal across its bottom cap, while the boolean copy averaged face normals instead, so the same dome shaded one way on screen and fed different normals to the CSG evaluator. Nobody could have written the test that would notice, because the test harness has no JSX plugin and no DOM environment -- nothing in a `.tsx` file is reachable from a test at all, which is around twenty thousand lines of this application including every mesh primitive and all three mesh-boolean backends. Moving a builder into a `.ts` module is what makes it testable, and this is the first of those moves.

- There are now tests that can see a primitive builder, and a test that compares the mesh ones against the exact ones. Each builder is measured against an independently derived closed form -- a prism's centroid a third of the way up its triangle, a pyramid's a quarter, a half-ellipsoid's three-eighths, a half-ellipse's `4b/3pi` -- and each tessellated kind is also asserted to come in *under* the smooth volume, since an inscribed polygon must. Separately, every kind that both the mesh dispatch and the exact OCCT dispatch in `serverCadSolids.ts` can build -- nine of them, counting a hexagonal pyramid and a tube and a ring -- is now built both ways and compared.

  Volume and centre of mass, never bounding extents. A bounding box cannot see a mirrored solid or a reversed winding, and a box or a cylinder is exactly invariant under the 180-degree error a negated yaw produces; that blind spot has already hidden two real bugs here, a box built from its corner instead of its centre and a rotation composition that disagreed with the editor in four of six cases while every test in the suite passed either way. The signed volume doubles as a winding check, since a mesh wound inside out is a hole as far as a CSG evaluator is concerned and is identical to the correct one by every extent you could measure.

  The three dispatches turn out to agree, within tessellation, on all nine kinds -- so this found nothing today. It is there for the day one of them is edited and the others are not, which is the day that has already cost this project three shipped bugs.

- Fixed server-side CAD geometry exporting to STEP at the origin instead of where the shape is. A fillet, chamfer or hollow done on the server stores its exact geometry in `cadBrep` with a `cadBrepFrame` saying where that geometry sits, and both things that read it -- STEP export and the editor's own CAD worker -- place the solid by subtracting the frame's centre and adding the shape's current one. The server recorded the *shape's* placement in that frame for geometry that is actually in the local frame every builder here produces, so the placement subtracted itself out: a part at x=25, z=-15, elevation=7 came back at 0, 0, 0. The frame now records the result's own bounds, which is what the editor's worker has always written for the same reason. Nothing caught this because a shape left where it was created subtracts zero, and because a misplaced part has exactly the size it should.

- Fixed `GET /api/v1/edges` answering `404 {"code":"api_disabled"}` from a production build, whatever token the server was started with. A route handler that exports only GET and touches no API Next recognises as dynamic is rendered at build time and then served from the full route cache; the build has no `SKETCHFORGE_API_TOKEN`, so the cached answer is the one that says the API is switched off. Every other route in `/api/v1` escaped by accident, by exporting POST or DELETE as well. Both read-only routes now export OPTIONS -- which is a true thing for an API to answer and, more to the point, stops the prerender, because the static-export build refuses every way of *declaring* a GET-only route dynamic. `tests/e2e/productionApi.e2e.ts` now builds and starts a real server, which is the only kind of test that can see this.

- The end-to-end suite's dev server now builds into `.next-dev` as the config intends. It inherited `NODE_ENV=test` from vitest, and the config only separates the dev compiler from the production one when NODE_ENV says development -- so two suites in the same run fought over `.next`, one failing its build and the other dying with "Cannot find module for page: /_document".

- Fixed a boolean cut turning a rotated shape twice. `POST /api/v1/booleans` builds each operand as an exact solid and then puts it where the shape sits with `shapePlacementMatrix`, which carries the rotation -- but the builder it called, `localSolidForShape`, baked the rotation in as well, so a rotated parametric operand was turned twice by the same rotation. A 20x20x12 wedge at yaw 90 was cut 3.33mm out of place in each of X and Z. #45 fixed *how* the two compositions compose and left them both in the call path, which made this cleaner rather than fixed.

- Nothing could have caught it. The volume is a rigid-motion invariant, a wedge's footprint is square so every extent was identical, and `meshYawDegrees` reduces a circular cylinder's yaw modulo its own side step -- so the shape most people would have tried was genuinely unaffected. `grep -rn "buildGroupFromSelection" tests/` also returned nothing: the server's boolean entry point had no test at all. It now has `tests/e2e/booleanRotation.e2e.ts`, which measures centre of mass against the editor's own placement composition.

- The two intents are now separate functions rather than a flag between them. `localSolidForShape` returns the shape's own unrotated frame, which is what its name and its docstring always said and what a caller holding a placement matrix needs; `orientedSolidForShape` is that plus the rotation, which is what a fillet, chamfer or hollow needs, because those store their result as a mesh with no rotation of its own. Both read one predicate, so they cannot drift apart again. The edge listing moved to the oriented solid too: an index is only a name for an edge if the listing and the treatment are looking at the same solid, and a turned shape's edge midpoints were being reported square.

- The REST API can now hollow a solid out. `POST /shell` offsets every face of a shape inwards by a wall thickness and takes the result away from the original, optionally leaving named faces off -- so a box becomes a shell, and a box with its top open becomes a tray. This is the biggest thing missing from a tool aimed at printing: a solid 20mm cube costs four times the filament of the same cube with a 2mm wall, and until now the only way to get one was to model the cavity by hand as a second shape and subtract it, which gives a constant wall only if you work the arithmetic out yourself. The operation is exact OCCT, and the result is stored the way a fillet's is -- a mesh to draw with the true geometry alongside it -- so a hollowed part still exports to STEP as real surfaces and can still be filleted afterwards.

- Faces to leave open are named by direction -- `top`, `bottom`, `left`, `right`, `front`, `back` -- or by index from the new `GET /faces`, which lists each face's area, surface type, centroid and outward normal. A direction means the outermost flat face pointing that way and only that one, which matters on a part that is already hollow: the floor of its cavity points up as surely as its lid does, and opening the floor rather than the lid looks exactly like nothing happening.

- A wall too thick for the part is refused with the project untouched. OCCT does not report that as an error: past the thickness that fits it variously returns an empty compound, a solid that fails its own validity check while reporting the correct bounding box, or -- worst of the three -- the original solid untouched, valid and the right size, having hollowed nothing. None of those can be told from a real answer by its extents, so the server weighs the result instead; hollowing always removes the cavity, and a result that weighs what it started at did nothing.

- Not every shape can be hollowed, and the refusal says which: a sphere, a torus, a cone, a tube's round wall and a loft each present one continuous curved surface with no separate faces to offset inwards, and the kernel refuses them at every thickness and at every reconstruction tolerance it offers. Boxes, cylinders and prisms, polygons, pyramids, roofs and wedges all work. For the rest, cut the cavity out with `POST /booleans` instead -- a different result, but one that works on a sphere.

- Both client libraries carry it with the server's own field names: `client.shell.hollow(...)` / `.tray(...)` and `client.faces.list(...)` in TypeScript, `client.shell.hollow(...)` / `.tray(...)` and `client.faces.list(...)` in Python, with `shell`, `hollow`, `tray`, `faces` and `faces_facing` on the project handle. The MCP bridge gained `sketchforge_hollow_shape` and `sketchforge_list_faces`, which drive the REST API against a stored project rather than an open editor tab -- hollowing is a server-side operation and there is no editor action for it yet.

- The loft and the gear are each now two modules rather than one, split along the line between the maths and the mesh: `loftProfile` and `gearProfile` hold the normalizers and the profile geometry and import no `three`, while `loftMesh` and `gearMesh` hold the `BufferGeometry` builders. `loftGeometry` and `gearGeometry` re-export both halves, so nothing in the editor moved. The server-side CAD builder needs the normalizers -- it builds a loft as an exact solid and has to settle the same questions about profile shape, rotation and top size that the drawn one does -- and because they shared a file with a mesh builder, asking for them dragged the renderer and a React-adjacent `@/i18n` type import into the server's dependency graph alongside them. It no longer does, which is a step towards an engine that can be lifted out of the app and reused by the MCP bridge and the client libraries without carrying a renderer. There is a test asserting that boundary, in the same shape as the one guarding `@/i18n` against import errors, so it cannot quietly come back.

- The normalizers both halves agree on are now tested directly rather than inferred from the vertices of a finished mesh, which is what made the split worth doing beyond tidiness. Two things came out of writing those tests. A polygon loft end is centred on its true circumcenter, and there is now an area-and-centroid assertion saying so, because a bounding box cannot see a profile that has been quietly recentred -- the same blind spot that hid a mirrored solid and an off-centre box. And a gear's root-circle floor, the 34% of the outer radius a bore may never exceed, turns out to be unreachable at any ordinary size: the tooth size is capped at 22% of the smaller dimension before the root radius is taken, which always leaves at least 56%, so the floor only binds on a gear under about a millimetre across. Both branches are now pinned, so whichever one a future change means to move, it will have to say so.

- Fixed server-side CAD turning a shape the wrong way, so a fillet, chamfer or STEP export of a shape that had been rotated came back facing somewhere else. The editor orients a shape with `THREE.Euler(rotationX, rotation, rotationZ)` in its default `XYZ` order -- the matrix `Rx * Ry * Rz` -- while the exact-solid builder negated the yaw and applied the three rotations in the opposite order. Of seven representative rotations, four disagreed with the editor: yaw alone came out mirrored, and every combination of two or more came out in the wrong order. Only single-axis pitch and roll were right.

  Nothing caught it because the shapes people fillet while turned are usually symmetric: a box, a cylinder or a sphere is unchanged by the 180-degree error a negated yaw produces, so the bug was invisible until an asymmetric shape -- a wedge, a roof, a cone with a top radius, a pyramid -- was rotated and then treated. There is now a test that measures the solid's centre of mass, which is the part a wrong orientation moves, against the editor's own matrix for all four of those kinds; a bounding box cannot see this, since mirroring a solid does not change its extents.

- The orthographic camera is now a saved workspace preference rather than something the viewport forgets. It had been local view state, so the one thing orthographic projection is for -- judging whether two edges actually line up, and reading a dimension off the screen without perspective quietly shortening it -- was available only until the next reload. It now sits with the other workspace settings, travels in the `.skf` project file, and goes through the same normalizer as everything else there: a project saved before the setting existed, or carrying a value this build has never heard of, opens in perspective instead of leaving the viewport asking for a camera it cannot build. The toggle and its `O` shortcut are where they were. Switching still frames the same scene from the same direction -- the orthographic frustum is built as tall as the perspective camera already saw at the orbit target, and coming back the camera is placed at the distance that sees the frustum the orthographic camera was showing, zoom included. That last part matters because zoom means two different things either side of the switch: an orthographic camera zooms by shrinking its frustum, since sliding it along its own axis changes nothing at all on screen. The conversions now live in `lib/cameraProjection.ts`, where they are covered by tests, rather than inline in the viewport.

- Fixed the snap grid being local to each shape rather than global to the world, which is upstream issue #117. It was local in two ways at once. The lattice was anchored on the near edge of the workplane -- `-width/2` on X, `-depth/2` on Z -- so a plate whose span was not a whole number of grid blocks snapped onto lines running through neither the world origin nor the lines a pointer drag or an arrow key snap to, the X and Z lattices could be offset differently from each other because width and depth are set separately, and resizing the plate slid the whole grid sideways under the model. The drawn grid had the same anchor, so on a 203mm plate there was no axis line through the origin to read at all, and the major line every fifth block moved when the plate was resized. Both now run through the world origin at multiples of the block size. The reference point was local too: whichever of the footprint's two edges happened to lie nearest a line was the one placed on it, and which edge that is depends on the shape's size -- so two shapes of different sizes came to rest on two different lattices and would not line up with each other, which is the symptom that was reported. The near corner of the footprint now always decides it, moved to its nearest line, so a snap still never shifts a shape by more than half a block. For a rotated shape that corner is the corner of its rotated bounding box, and for a shape whose footprint is not centred on its origin it is the footprint's corner and not the origin, so what lands on the grid is the thing you can see.

- Designs now export as 3MF, which is what a modern slicer would rather be given than an STL. The STL writer throws away two things the slicer then has to guess at: the unit, so a design is a pile of unitless numbers that happens to be read as millimetres, and the colour, along with the boundary between one shape and the next -- a selection of five parts arrives as one anonymous triangle soup. A 3MF is an OPC package (`[Content_Types].xml`, `_rels/.rels`, `3D/3dmodel.model`) whose model declares `unit="millimeter"` and carries one named `<object>` per shape, each with its own mesh, plus a `<build>` placing each object with its own transform. Each object is written in its own frame -- centred on its footprint and resting on z = 0 -- and the build item carries the placement, which is the shape a slicer expects a part to arrive in. The archive pins its ZIP timestamps the same way the `.skf` writer does, so exporting the same design twice gives the same bytes.

- Shape colour travels with the 3MF, as the core specification's `<basematerials>` and a `displaycolor` per object, not as the materials-and-properties extension. The extension would have to be declared in `requiredextensions`, and a reader that does not implement it is then required to reject the whole file; `displaycolor` is part of the core, so a reader that ignores colour still gets correct geometry. Nothing in the file depends on an extension namespace.

- A shape can now be given a material -- PLA, PETG, ABS, ASA, TPU, nylon, polycarbonate or resin -- and the inspector shows what the part would weigh and what it would cost. The weight is volume x density, taken from the solid mesh by the signed-tetrahedron sum rather than from the bounding box, so a cone weighs a third of the cylinder around it. Each preset's density is the figure from the manufacturers' data sheets, in g/cm3, cited in `lib/materialPresets.ts`; the price per kilogram is a setting with a sensible default per material, editable next to the readout and saved with the project, since nobody's filament costs what a hardcoded number says. A hole has no weight of its own and says so instead of pricing the material it removes. The weight is for a solid part, which is the upper bound -- a sparse infill prints lighter.

- A material round-trips through the `.skf` project format as a plain field on the shape, needing no new asset and no format version bump, so a project saved with one still opens in a build that has never heard of materials: the reader validates the fields it knows and carries the rest through untouched. A material id from a newer build is kept as it was found rather than coerced to PLA, and simply goes unpriced.

- The editor's boolean cuts are now exact, which fixes upstream issues #118 ("combining a negative space cylinder with a block results in a broken mesh") and #111 ("Tapered Box combined with other object results in square not tapered hole"). Both were the same thing: the cut was a mesh operation, so every operand reached it as triangles. A negative cylinder arrived as a ninety-six-sided prism and left ninety-six planes where there should be one cylindrical face -- which is both the broken mesh and the reason a later fillet of that pocket had nothing to blend -- and a tapered cutter's slope was lost wherever a path stood a plain box in for it, leaving a square hole of the taper's widest section. The browser already carries OCCT for fillets and chamfers, so the cut now goes to that kernel in the same worker, with each operand built from its own parameters: a cylinder is a cylinder and a taper is a frustum. Measured on a 40x40x10 plate, a 12mm pocket 4mm deep now removes 452.39mm^3 against the arithmetic's 452.39 rather than 465.71, and a 20mm-to-10mm tapered pocket removes 1400.00 rather than 2400.00 with its walls sloped rather than vertical.
- A cut that comes out exact no longer needs the cutter grown first. The mesh path pads every cutter by 0.05mm because a mesh CSG resolves two coplanar faces unpredictably; an exact cut resolves them by construction, so a pocket asked to stop flush with a face now stops there instead of 0.05mm past it -- 5.75mm^3 of plate that used to be quietly eaten out from under a flush pocket's floor. The result also keeps its exact geometry alongside the mesh, as a filleted shape does, so a fillet, a chamfer or a STEP export of a cut part reads true surfaces rather than the triangles that were drawn for it.
- The mesh booleans are kept whole as the fallback, because this app also ships as a static export and as a desktop build where there may be no worker and no kernel to load. A kernel that never loads, a shape whose geometry cannot be built from parameters (text, gears, sketches, mirrored shapes), or a hole that misses its solid all fall through to exactly the cut the editor made before, and the request is abandoned after fifteen seconds rather than leaving a group half-made.

- Fixed an editor tab opened at `http://127.0.0.1:3000` being unable to reach its own MCP route, so it never appeared in `sketchforge_list_editors` and every LLM tool answered as though no editor were open. The route compared the browser's `Origin` against `request.url` as whole strings, but Next rewrites that url's hostname to `localhost` whatever the `Host` header said -- so a `127.0.0.1` tab failed the comparison and every heartbeat came back `403`, with nothing in the interface to say why. Origin and request now have to agree on being a local host and on the port, which is the check this was always meant to be. `localhost` worked, which is the only reason this was survivable.

- Fixed the desktop installers never being attached to a release, which is why 1.2.0 and 1.2.1 both have none even though every build succeeded. The attach job still assumed it owned the release, as it did before releases were driven from `main`: it refused to continue when the release already existed and was not a draft, and a later step asserted the release *was* a draft. release-please now creates the release when its pull request merges, and creates it published -- because GitHub does not make the git tag for a draft -- so both checks rejected every release there will ever be. The job now attaches to whichever release the tag has, draft or published, and only creates one when nothing is there.

- A dispatched desktop release now builds the released tag rather than whatever `main` says at the time, falling back to the checked-out commit when the tag does not exist yet. Re-running an old version used to package current `main` and label it with that version, which is precisely what recovering a missed release asks for. The tag check alongside it no longer fails when the tag points somewhere other than the dispatch commit, since that is now deliberate.

- The MCP bridge is now a published binary, so an AI client can start it with `npx -y -p @constructorfleet/sketchforge3d sketchforge-mcp` instead of needing a clone of this repository and a built client. It moved from `scripts/` into the client package as `mcp/server.mjs`, which is also where its two macro tools can find the runner they spawn -- previously they located it by walking up to the repository root, which does not exist in an install. A Python macro now relies on `sketchforge3d` being installed from PyPI, since only a checkout carries the Python source. `npm run mcp:sketchforge` still runs the same file from a checkout, and the version the bridge reports is the package's rather than a hand-written `0.1.0`. The Claude Desktop and Codex example configs use the npx form.

- The REST API now reads back everything it can be told, which it had been promising and not doing. A shape summary carried only placement, size, rotation, the three flags, `sides` and `text`; every other parameter a kind is built from -- a tube's wall thickness, a cone's radii, a gear's teeth, a loft's profiles, text's font, the taper fields -- was dropped on the way out, so reading a shape, changing one number and sending it back lost all of them. Threads and revolves fared worse: they are stored as a mesh carrying a sketch profile and revolve settings, and the summary showed none of that, so a client could not read a thread's pitch, could not change the pitch of a thread it had just created, and could not tell a thread from an imported STL. The summary is now driven by the same table that builds a shape from a request, so a parameter the API can set is a parameter it reports, and a revolve also reports its sweep under `revolve` and the outline it ran round under `profile`.

- `kind` still reports what the project stores -- a `cube` is a box whose sides match, and a revolve is a mesh -- because that is what the editor shows and what every existing caller already reads. The missing half is a new `requestKind`: the kind a `POST` would need to build the shape again, which is `box` for a cube and `revolve` for a thread, and which is absent for a shape no request reproduces, such as a boolean cut or an imported mesh. That absence is what distinguishes a thread from an STL, which by stored kind alone was impossible.

- `PATCH /shapes` now applies the fields it reports, or refuses them by name. It had applied only name, colour, placement, size, rotation and the flags; anything else -- `sides`, `bevel`, a thread's `pitch` -- was accepted, answered `200`, and changed nothing, which is the one answer a script cannot tell from success. A parameter belonging to another kind, a sweep setting on a shape with no sweep, and a field this version has never heard of are now all refused with `422` and a `fields` list naming them, and the request is refused whole so a typo cannot half-move a shape.
